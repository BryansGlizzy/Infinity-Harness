The unabridged history, with every live test and step-by-step note, is in [archive/master-plan-full-2026-11-07.md](archive/master-plan-full-2026-11-07.md). ## 1. What it is

A local-first **daemon + web UI** (plus a VS Code extension, a terminal UI and the `ih` command line) that runs the coding agents already installed on the machine (Claude Code, Codex, Kimi Code, Antigravity `agy`, OpenCode on NIM or a local model) as workers on a **live, growing kanban tree**.

- **An orchestrator agent plans:** it splits a goal into cards (optionally handing a big chunk to a *lead* agent). Two or more orchestrators plan as a *council*.
- **Kev classifies:** a self-hosted judge model scores each card's work type, complexity and need for review, and scores landed work.
- **Code routes:** deterministic code picks the agent from availability, quota and learned success. No LLM is in the scheduling loop.
- **Each card runs in its own git worktree** (or, for a plain folder, directly in it) and lands through a serial merge queue, as a GitHub PR or a local merge.
- **Agents coordinate** through one board MCP server: messages, file leases, shared notes, handoffs, requests for new tools.
- **Swarms cooperate:** daemons on different machines connect, share the projects they choose, and send each other requests that the other side's orchestrator answers.

**Status 2026-11-13:** Phases 0 to 9 are built (Phase 9, the MCP hub and agent notes, is §12); 302 automated tests pass. Status 2026-11-11: Phases 0 to 8 were built with 290 tests (they run on fake agents; Phase 8 also checked the new parts against real Claude, Kimi, Agy, Codex and NIM sessions and in a real browser). Real multi-card goals have run end to end (a Rust port of the passkey-manager project, and a goal that planned, built, summarised itself). **Not yet done: a full day of real unattended work (the Phase 6 exit)**, which is the natural next step. §8 lists what has and has not been checked on real agents.

## 2. Principles

1. **Drive the real CLIs; never reimplement them or touch their credentials.** Each harness runs as itself, logged in by its owner (native features, subscription billing, inside vendor terms).
2. **The model classifies, code routes.**
3. **Pull, don't dump:** agents get a small starting prompt and query the board for context.
4. **Everything is an event.** An append-only log drives the UI, replay, audit and metrics.
5. **Transport-agnostic executors:** `local` now; `ssh` and `docker` later.
6. **Configurable by default:** retries, budgets, thresholds, permissions, depth limits and reserves are settings with visible defaults.
7. **Ask, don't take** (for agents): spawning agents, adding MCP servers or skills, tool grants and installs wait for a person. Between swarms, nothing another swarm wrote is read by an agent before its own operator accepted that swarm.

## 3. Locked decisions

| Area | Decision |
|---|---|
| Scope | Local team tool, one repo per board, single local owner (no login; the data model carries `user_id`; accounts with subtree scopes come later). |
| Pools | Subscriptions: Claude Pro, Codex (ChatGPT plan), Kimi Plus, Google AI Pro (agy). API pools: NVIDIA NIM (40 RPM), local Qwen via OpenCode. Groq free (~8k tokens/min, 1k requests/day) is **fast lane only**. |
| Limits | One limiter for every pool: windows (rpm, tpm, rpd, 5h, 7d, concurrency, budget) **warn at 80%, halt new work at 95%**; API traffic goes through the daemon's gateway so every request is counted. |
| Judge | Self-hosted **Kev** (`kev-9b`, Unsloth Decision API) at `$KEV_URL`. Without it, cards route on default estimates and nothing is scored. |
| Embeddings | `$EMBEDDINGS_BASE_URL`, EmbeddingGemma 768-dim (query/document prefixes, similarity floor 0.65). Without it, search is full-text only. |
| Claude integration | Interactive PTY with hooks (not Channels, not `-p`): typed prompts at turn boundaries, Esc for urgent, `PreToolUse` hook for policy, status line for the 5h/7d windows. |
| Autonomy | Fully automatic: cards start when unblocked, auto-approve inside the worktree policy. Retry and escalation counts are settings. |
| Messaging | Queued to the next turn boundary; `!urgent` interrupts. No group chat. |
| Git | Worktree per card, **enforced** leases, a serial merge queue per board; **merge commits, not squashes** (a card that waited on another already contains its commits; a squash would make dependents conflict). |
| Naming | Infinity Harness everywhere: `@ih/*` packages, `ih` command, `IH_*` settings, `.infinity-harness/` state, `infinity-harness.db`, `ih/` branches. An install from before the rename (Meta-Harness: `MH_*`, `.meta-harness/`, `mh/` branches) is carried over on first start by `apps/daemon/src/legacy.ts` (folder moved, database renamed, card paths and git worktrees repaired, `MH_*` still honoured and reported). The archived documents keep the old names. |
| Storage | SQLite via `node:sqlite`, hand-written migrations (15 so far). |
| Stack | TypeScript run directly by Node 24+ (type stripping, no daemon build step), pnpm workspaces, Fastify 5, React 19 + Vite + React Flow + xterm.js, `node:test`. |
| Notifications | UI, VS Code and TUI only (no phone/Slack yet). |

Models are discovered from each harness (ACP `session/new` config options; Claude's aliases) at daemon start and on **Refresh models**. Reasoning levels likewise (Claude `--effort` low..max; Kimi `thinking` low/high/max; agy `thinking_level` low/medium/high; OpenCode `effort`); a level the harness does not offer is reported and skipped. **A harness's own default applies when an agent has no level set, and it can be the slowest one: Kimi's is `max`, Agy's `high`, Codex's `high`** (found in Phase 8: Kimi's model time was 8 to 11 s a step; set a lower level on agents meant to be fast). Everything installs in the home directory, no sudo. `tmux` is not needed.

## 5. How it works

```
 Clients: web UI · VS Code extension · TUI (`ih tui`) · `ih` CLI     (all use @ih/client: REST + replaying WebSocket)
   │
 Daemon (Node/TS)  :7420 operator API + UI · :7421 LLM gateway · :7422 federation (signed routes only)
   Event log ─► projections          Settings/permissions · Approvals · Budgets
   Scheduler ◄─ Router (Kev) ◄─ Limiter (all pools)      Refinery (review, merge queue, landing)
   Runner (sessions, messages, leases) ─► Adapters [claude | codex | kimi | agy | opencode]
   Context store (notes, FTS + vectors) · Board MCP server · Telemetry (OTLP) · Fast lane · Federation
   Every worker: own worktree + branch · board MCP injected · isolated harness config
```

### 5.1 Adapters
One interface (`startSession`, `prompt`, `cancel`, `close`, `listModels`/`probe`); the daemon never special-cases a vendor outside its adapter. Claude is a PTY (attachable from the clients); the rest are ACP. Kimi 2.5 advertises HTTP MCP and the board server connects fine.
- **OpenCode** hosts many concurrent sessions on different models in one process; each API endpoint is one pool. It generates `opencode.json` from `.env` (via `OPENCODE_CONFIG`, nothing written into repos), pointing every provider at the gateway. Its base policy allows everything, so the config adds `ask` rules for edit, shell, web and external directories; a refused permission ends the turn as `cancelled` and the runner resumes it with the refusals listed (up to 3 times). It lists MCP tools in a truncated catalog, so prompts name the board tools. NIM and local have no web access (research cards never go to them).
- **What the ACP harnesses stream, and what we keep** (probed raw in Phase 8; `packages/adapters/src/acp-agent.ts`). Messages and thoughts arrive as chunks (Kimi: hundreds per task) and are merged once a second. A tool call carries its title, kind, files and status; its **output** arrives differently per harness and is now kept as `tool_output` events (`toolOutput`, clipped to the head and tail of 8 KB): Kimi puts the whole text in `rawOutput`/`content` when the call completes (its `content` while running is the arguments as JSON, never output); Agy sends `rawOutput.combinedOutput` and the exit code at completion; Codex streams `_meta.terminal_output_delta` and ends with `terminal_exit` (only the tail of the output, not the opening); OpenCode puts the text in `content` and the exit code in `rawOutput.metadata.exit`. None of them streams a running command's output as it happens except Codex. Kimi repeats `tool_call_update … in_progress` several times a second with nothing new (9,000 events on one card), so pure repeats are dropped (`isRepeatedToolUpdate`). OpenCode's silent retries of a failing provider (`session_info_update` with `opencode/retry`) become visible `notice` events.
- **Client terminals (`terminal: true`) were tested, not enabled.** Only Kimi uses them: it asks the client to create, poll and release a terminal, which would give true incremental output and let the daemon decide where the command runs (a path to the Docker executor), at the price of owning process cleanup and enforcing worktree confinement at spawn. Agy and Codex ignore the capability (Codex would otherwise lose its own sandbox). We still send `terminal: false`. Recommendation: try it for Kimi alone, later; do not move the ACP harnesses into a PTY (they are structured protocols; the tool-call data routing and metrics use would be lost).
- **Groq** is not an OpenCode pool (a first OpenCode turn is ~8.2k tokens, over its per-minute limit) and must send a normal User-Agent (Cloudflare 403 otherwise).

### 5.2 Data
SQLite, one file (`.infinity-harness/infinity-harness.db`, or under `IH_STATE_DIR`). Tables: boards, nodes (cards), edges (dependencies), sessions, events (append-only; everything else is a projection), usage_events, leases, messages (with `dismissed_at`), settings (JSON per board), artifacts (+ FTS5), outcomes, approvals, pool_samples, pool_ejections (pools taken out of rotation), and the federation tables (peers, shared projects, cached peer projects, requests, nonces, settings). Migrations run on start.

### 5.3 Board MCP tools (one server, filtered by role permissions)
- **Work & tree:** `whoami`, `list_cards`, `create_subtask` (also `delegate`, `blocked_by`, `needs_network`, `grants`), `update_subtask`, `add_dependency`, `report_blocked`, `escalate_to_human`, `propose_split` (council members).
- **Messaging & files:** `post_message` (to a card or `human`), `read_inbox`, `ask_agent`, `reserve_paths`, `release_paths`, `who_holds`.
- **Context:** `search_context`, `get_artifact`, `put_artifact`, `write_handoff`, `get_docs` (serves `docs/agents/`).
- **Asking for more (each waits for a person):** `spawn_agent`, `propose_mcp`, `propose_skill`, `request_grant`.
- **In an editor:** `ide_ask`, `ide_diagnostics`, `ide_show_diff` while a VS Code window is attached.
- **Other swarms:** `list_peers`, `find_peer_projects`, `request_peer`, `peer_request_status`, `reply_to_requester`, `report_milestone`, `propose_project_card`.
Not built from the original plan: `list_ready`/`claim_task` (the scheduler assigns), `assign`, `request_review` (the refinery reviews).

### 5.4 Routing and scheduling
1. The orchestrator creates cards with specs, a proposed work type and acceptance criteria. A fast-lane lint bounces vague specs back. The planning prompt says how many cards the board can run at once and how to cut for width (own files per card, `blocked_by` only for real code or output dependencies, a small foundation card, integration last); `create_subtask` and `add_dependency` reply with the plan's wave count and, when the plan is a chain the board could have run side by side, name the longest chain and ask the planner to justify each link (`apps/daemon/src/plan-shape.ts`).
2. Kev classifies each card (work type, complexity 0 to 4, needs-review) in one call; defaults when Kev is down.
3. **Filter:** role (lead cards go only to leads), routing rules (inherited down the tree, per card), capability (`needs_network` skips Codex; research skips NIM and local), free slots, pool state (never halted or locked, and not **out of rotation** when its endpoint stopped answering, §5.13), Claude and Codex reserves, agent and board budgets.
4. **Score:** success (per-model prior blended with recorded outcomes) × headroom × scarcity × load × the operator's per-agent weight (`agentWeights`, default 1; a boost above 1 applies only to cards within the agent's capability, 0 = off for auto-routing), with a bonus for the previous pool. Agents that failed the card rank ×0.2.
5. A card waits for its dependencies (a planning card counts only when its whole subtree is finished), starts with their branches merged, and waits `rerouteAfterSec` for its previous pool before moving on.
6. **Stall watchdog:** no agent activity for `stallMinutes` (5) cancels the turn, locks the pool for 10 minutes and re-routes with the work committed. Observed quota errors lock a pool until they lift.
7. **Best-of-N** (off by default): a big card is raced by 2 to 3 agents; Kev scores the diffs; losers are discarded.
Agents are **profiles** `{id, pool, model, reasoning, role, delegatesTo, enabled}` in board settings; quota, slots and limiter state stay per pool. Every pool without its own worker gets an implicit one. **New boards start with the subscription workers switched off** (Agents view); with only NIM and local enabled, research cards have no taker. Settings saves are validated (known targets, no delegation cycles). The orchestrator is the first enabled orchestrator agent whose pool is open, falling back to a lead and then any open pool. **Councils:** with two or more enabled orchestrators each proposes a split, Kev picks, each plans its share, then they cross-check each other (not on direct boards).

### 5.5 Messaging, leases, landing
- Messages queue to the next turn; urgent ones interrupt. `ask_agent` prompts an idle agent, or the fast lane answers a busy one from its notes.
- **Leases** (`reserve_paths`) are enforced where the harness asks first (Claude hook; OpenCode and agy permission steps) and at merge time. Kimi and Codex edit inside their cwd without asking, so leases do not stop them at edit time.
- **Refinery** (serial per board): optional cross-provider review (Kev needs-review ≥ 0.6; reviewer on a different pool in a read-only copy) → queue → merge the base branch in → run the board's test command → land (GitHub PR opened and merged, or a local merge commit). Conflicts and failing tests go to the author, then to another agent with a handoff, then to a person. You can instead review a card yourself (web, VS Code, TUI: approve, request changes with line comments, land now, try it in your checkout; the "Hold cards in Review for me" setting makes that the rule). Build output (`__pycache__`, `node_modules`, caches) is never committed.
- **Direct mode:** a folder that is not a git repository gets no worktrees: agents edit it in place, cards end Done, up to three workers at once by default (`directParallel`; leases keep Claude, OpenCode and agy apart, Kimi and Codex rely on each card owning its own files), no councils.
- **Worktrees** live under `.infinity-harness/worktrees/<board>/<card>` (`IH_WORKTREES_DIR` moves them); an optional setup command runs once in each. A folder in the way is moved aside, never deleted.

### 5.6 Context and learning
- **Notes** (spec, summary, decision, contract, handoff, finding, note) are captured automatically or written with `put_artifact`, tagged and summarised by the fast lane, versioned, stamped with the branch head, searchable by FTS5 and vectors fused by reciprocal rank (brute force over BLOBs; falls back to full-text when embeddings are down). Scopes: card, subtree, board.
- **Handoffs:** every reassignment writes a structured handoff (state, decisions, blockers, files, next steps) that is also the new agent's first message.
- **Learning:** Kev scores landed work against the acceptance criteria; outcomes are kept per pool + model and work type (landed: quality × scope × 0.9^changes; failed landing 0.4/0.2; failed run 0; a reported block waits for you to weigh it: pass/fail/ignore; quota errors and an unreachable provider don't count). Routing blends them with per-model priors (counted as 3 outcomes), editable per agent in Settings → Learning.

### 5.7 Quota, budgets, fast lane
- **Pool state** comes from its fullest window: open <80%, warn ≥80% (ranks lower), halted ≥95% (subscriptions get no new cards; API pools queue at the gateway), locked (an observed lockout until its reset). Sources: Claude's status line, Codex's usage, the gateway's counts for API pools, observed errors. Force a pool to 95% to watch work flow elsewhere.
- **Usage** is attributed to board, card, agent and model: Claude via OTLP (`/v1/metrics`, enabled per session), ACP harnesses when they publish usage, the gateway for API pools. Cost is only what Claude reports. The Metrics view rolls it up the card tree.
- **Budgets** (Settings → Budgets) cap a board or an agent in tokens or dollars per day/week/total, inside the same limiter (80% warns, 95% stops new work; running turns finish). Pool history keeps a week of minute samples.
- **Fast lane** (Groq → NIM → local, per-job token caps): narrator, `ask_agent` quick answers, query rewrite, artifact tagging, commit/PR text, test-failure triage, spec lint, notification text, project-card wording. Kev decides; Groq writes.

### 5.8 Safety and isolation
- **Worktree confinement:** every tool call naming a path outside the card's worktree is refused (shell commands are checked lexically for redirects, `../`, `~`, absolute paths). Shared tool locations are allowed (`/tmp`, `PATH` dirs, toolchain folders such as `~/.cargo`, `~/.platformio`, `~/.cache`, extra *Tool paths*; the repo's git dir; each harness's own state); other projects, the main checkout and the rest of the home are not. Refusals are reported to you naming the path and where to allow it, and agents are told a refusal is policy, not a human. Codex runs in its own sandbox (worktree, `/tmp`, the shared roots as writable roots, no network).
- **Isolation per harness:** Claude runs with `--strict-mcp-config` and `--setting-sources project,local`; agy runs with an isolated `HOME` that links only the login, toolchains and git config (its server once loaded the user's IDE MCP servers, one failed, and every card "succeeded" doing nothing; the smoke test now checks the diff); OpenCode uses the generated config; Kimi has none yet. Provider keys and parent Claude Code markers are stripped from agent environments.
- **Governance:** an approval queue (escalations, new agents, MCP servers, skills, tool grants, tool installs, optionally agents' requests to peers). Approving an install runs the grant's own `install` text from settings, never anything an agent sent. **Tool grants** are extra MCP servers per card (`browser` = agent-browser, approval by default; `computer` = agent-desktop, off by default). Agent-facing docs are in `docs/agents/`.
- **API access:** the daemon listens on loopback. An API token (`.infinity-harness/api-token`, 0600) is required from other machines (or from everyone with `IH_REQUIRE_TOKEN=1`); Host and Origin checks stop other websites from driving it; a wrong token is refused. **Agent endpoints (`/mcp`, telemetry, Claude's hook) take their own per-session token and are open to local processes.** (A bug until 2026-11-07 refused every agent's session token as an invalid API token, which broke all board tools on a normally running daemon; the tests ran without that layer. Fixed and tested through the real layer.) **Known gap:** an agent can still call the operator REST API from this machine without a token (unless `IH_REQUIRE_TOKEN=1`).
- **Not a sandbox:** shell commands run unsandboxed in the worktree; container isolation (Docker executor) is the real boundary and is not built.

### 5.9 Restarts
On start the daemon closes sessions with no process, puts interrupted workers back in Ready (work kept), blocks interrupted planners for you (re-planning could duplicate cards), and posts one message. A graceful stop records which sessions it cut off; when such a card runs again on the same pool the harness conversation is picked up where it can (ACP `loadSession`; Claude `--resume`). Cards in Review or Merging are redone by the refinery.

### 5.10 Clients
- **Web UI:** Tree (React Flow: draggable nodes, live animations, themes Clean / Frutiger Aero / Metro / Metalheart / Glassmorphism; each node has a **▾ that opens a live activity box** under it: confined, resizable (size remembered), following the latest output, per-board open state, fed by one shared event bus), Board, Agents (with **pool health, Test and Put back in rotation**), Pools, Metrics, Swarms; card panel (Activity with **command output under each tool call**, retry notices and a follow-the-bottom list; Changes; Context; Terminal; your review; the facts and routing folded under **Details** so the list always has room); tabbed Settings with defaults and Reset; a **file tree** down the left (read-only, lazy folders, git markers, a card's worktree selectable) with a viewer; `@swarm/project` completion in goals and card messages; board removal. **Messages for you** can be cleared (one, or all; `POST /api/boards/:id/messages/dismiss`; stored as `dismissed_at`, the message stays in the card's log) and a click opens what the message is about (its card, or Approvals, Swarms, Agents or the settings tab that fixes it). The tree rebuilds its nodes on every update but keeps each node's measured size (fresh nodes are hidden until re-measured, which made the whole tree flicker or stay blank under a busy run).
- **VS Code extension** (`apps/vscode`): binds the open folder to its board; Cards and Needs-you views; chat per goal; plan from a selection or the file's problems; review in the diff editor with line comments; approvals; IDE bridge for agents; attach to a Claude terminal; board in a tab; a ✕ on each message and a Clear all button, messages that name a card open it, and *Pools…* tests a pool or puts it back; the status-bar tooltip shows each pool's health. Publisher id and license fields are still placeholders.
- **`ih` CLI:** status, boards, cards, plan, add, needs, approvals, approve/deny, message, review, land, move, cancel, changes, diff, events, watch, terminal, pools (with a MODEL column), **pool test|restore**, **messages [clear]**, weight, metrics, machine, swarm, peer, project, request, board remove, skill. JSON when piped, tables at a terminal, exit codes 0/1/2.
- **TUI** (`ih tui`, no dependencies, own renderer, mouse-first with the key on every button): Needs you (messages have **Clear x** and **Clear all X**), Board, Pools (health per pool; **t** tests, **b** puts a pool back in rotation), Files; machine and board switchers; dimmed cached state when a machine drops.
- **Other machines** are reached over SSH, never by opening the daemon to the network: `ih machine add user@host` saves a profile; `ih --machine <label> …` runs through an `ssh -L` forward `ih` makes and re-makes with backoff (BatchMode; load your key into `ssh-agent`).
- **Where each client stands.** The daemon-side changes reach every client (the planner prompt, three direct workers, no-blame outages and ejection, final summaries, the events fix). Command output, retry notices and the live tree box are **web only** by design: the VS Code chat is the conversation (what agents said, questions, status changes) and the TUI has no per-card activity screen; `ih watch` and `ih events` carry the raw events, `tool_output` included. Clearing messages and pool health/test/restore exist in all four clients; the settings toggle for the final summary is web only (any client can change it through the settings API).
- **Skill file** (`skills/infinity-harness/SKILL.md`, `ih skill install`) teaches an agent outside the board how to use `ih`, and lists the decisions an agent may never take for you (approve, deny, review, land, move, cancel, worktree removal, **putting a pool back in rotation**, machines, peers, board removal).

### 5.11 Swarm federation (Phase 7)
A **swarm** is one daemon with its boards. Only structured data crosses between swarms (knocks, project cards, requests and their status), never chat and never code.
- **Port and transport:** a second loopback listener (`IH_FED_PORT`, default **7422**; `off` disables) serves only signed `/fed/*` routes, so an SSH account for a peer can be limited to it (`PermitOpen`). Peers are reached by an outbound SSH forward we make (`MachineConnection`, health-checked on `/fed/health`) or a local URL of your own tunnel. Nothing needs an inbound port; both directions travel over the link the knocker opened.
- **Identity:** an ed25519 key in `swarm-key.json` beside the database (0600; `IH_STATE_DIR` gives a second instance its own). Swarm id and the fingerprint operators compare are derived from the key. Every request is signed over method, path, time (5-minute window), nonce, recipient and body hash; answers are signed over the request's nonce; nonces are stored.
- **First contact (the knock):** an unknown swarm gets only a silent unsigned `pending`; its text is **quarantined** (shown to the operator, to no agent, not searchable). The operator compares fingerprints and accepts (pins the key, releases its directory), denies (it may knock again) or blocks. An expected fingerprint can be typed when adding a peer; a different key is refused. Peers: pending → verified → trusted (or blocked). A peer that connected to us can be given an address later ("Connect back", `ih peer address`) without losing trust.
- **Project directory:** per board, a project card (what it is, what it **provides**/uses, stack, whether it takes requests) is drafted from the README and manifests (fast lane words it; or the orchestrator, switchable), edited and published by the operator at *basic* or *full*; a peer gets at most basic until trusted. The operator previews exactly what a peer receives. Cached cards reach agents as data (`find_peer_projects`, the planner's prompt).
- **Mentions:** typing `@` offers `@swarm/project`; the daemon, not the client, resolves a named project in a goal or card message and appends its card as data, with a reminder to use `request_peer`.
- **Requests:** `pending` (receiving operator decides) → `in_progress` (a goal for that board's orchestrator, marked as outside text, with instructions to answer) → `landed` (with the answer text, a commit/PR or version) → `done` (the sender confirms; or the waiting card confirms when it finishes). Also `needs_info`, `declined`, `cannot_reproduce`, `cancelled`, and **reopen** (send a landed result back). Delivery is idempotent by the sender's id. Limits: 20 requests an hour and 10 waiting per peer; hop list ≤ 6 and loops refused; the last hop must be the signer.
- **Orchestrators answer each other (decided 2026-11-07):** the receiving orchestrator answers simple things itself and replies with `reply_to_requester(answer, done?)` (the answer, up to 20k characters, reaches the asking card word for word), or plans cards and replies with the result; a goal that finishes without a reply sends its cards' summaries. Agents' requests go out **without approval by default** (`peerRequestApproval`, off; on makes each wait). A blocking request parks the card (`pipeline.waitingOn`, held in Ready by the scheduler) and it resumes with the answer; when it finishes, the request is confirmed.
- **Auto-accept:** only for a trusted peer; switching it on fills 300k tokens a request and 2M a day unless given; a request naming more waits for a person; you are told of each and can decline it. Untrusted peers can never be auto-accepted (checked again at receipt).
- **Budgets for requests:** a request's budget (sender-set, operator-editable) and the peer's daily cap are compared with its goal's usage: 80% a message, 95% its unstarted cards are held; the day's cap holds all of that peer's requests. Milestones are listed by the sender and ticked by the receiver (or `report_milestone`). Dollars count only where a harness reports cost.
- **Not done:** the peer profile's counted history and markdown rendering; automatic dependency-to-`provides` matching; per-peer spend in the Metrics view; an orchestrator cannot wait for a peer (its requests never hold it; workers and leads do); no resume into the old session (a held card starts a new one).

### 5.12 Files and board removal
- **File tree:** `GET /api/boards/:id/files?path=&card=` and `/file`: read-only, `.git` hidden, folders first, git markers, at most 3000 entries a folder and 1 MB a file, nothing outside the root (`..`, absolute paths and links that leave are refused).
- **Removing a board** (web, VS Code, TUI, `ih board remove`): **forget** (records, events and the harness's own card worktrees go; the project folder and branches stay; open peer requests are declined/withdrawn) or **delete on system** (also deletes the folder; the board's name must be typed back, checked by the daemon; refused for the home folder or anything holding it, the top of the disk, anything holding the harness, a symlink, or a folder overlapping another board). A board with a card in the merge queue cannot be removed.

### 5.13 Finishing a goal, and knowing a pool is up
- **Final summary** (`apps/daemon/src/final-summary.ts`, setting `finalSummary`, Settings → Tools, on by default). When a goal's cards are all done (a root orchestrator card turns Done, by the refinery or the council), **the orchestrator that planned the goal gets one more turn on the goal card itself**: its parked session is given the request (`Runner.promptIdle`, a turn with exactly that prompt, no message wrapper), so it writes the report from what its cards already reported to it, with no new card and no new session. The request says what to write and what not to do: no reading files, running commands, searching, opening notes or re-verifying; where the cards did not say something (how to run it, whether tests ran) it writes "not reported". It carries only a digest (cards, agents, landed commits and PRs, titles of decisions, contracts and findings). If the session is busy it is waited for (up to a minute); if it is gone (the 15-minute idle timeout, a restart) the **same goal card is run again** with the cards' own last reports (trimmed to their ends, at most 30k characters) and the notes' text in the prompt. (Until 2026-11-13 this started a second orchestrator on a new `Summary: <goal>` card, whose prompt told it to check the repository and the board: it re-researched everything and burned tokens. Older goals may still have such a card, linked by `summaryOf`.) The report is that turn's last message: sections outcome, what was done, how to run and verify it (what the cards said they ran), decisions, open issues, and **reference documentation** (files and references the cards reported, as reported, not checked; "None" otherwise). When the card returns to Review the daemon files it on the goal as a `Final summary: …` artifact (Context tab), clears `pipeline.finalSummary.pending` and posts it to Messages for you (the notice names the goal, so the VS Code goal chat shows it). It runs once per goal, and again only if more work cards finished since (the card turns Done twice; the guard is the covered-card count); a one-off task without cards never triggers it. If it cannot start (budget) or the turn is blocked or empty, a message says so and tells you to message the goal card for the report: Run on a goal card would plan it again and could duplicate its cards.
- **Pool health** (`apps/daemon/src/health.ts`). API and local endpoints are checked every minute (a request to their `/models`; any answer below 500 is "up", a refused key is noted, a timeout says how long it waited); a subscription harness is checked on request by starting it and listing its models (this proves it is installed and signed in, not that inference works). The Agents view shows online with the answer time, no response, or not checked, with a **Test** button (also the TUI Pools screen, VS Code *Pools…*, `ih pool test`).
- **An unreachable provider is not the model's fault, and takes the pool out of rotation.** A run that fails with a message meaning the provider could not be reached (`PROVIDER_DOWN_PATTERN`: `fetch failed`, `ECONNREFUSED`, 502/503/504, `upstream error`, a harness's retry notice…) is never recorded as a failed run (it used to score 0 against the model) and does not count as the author's fault when a card escalates. For API and local pools the daemon checks the endpoint at once (the first retry notice is enough, so it no longer takes minutes); if it really is down the pool is **ejected** (`pool_ejections`, survives restarts): routing marks it ineligible with the reason, cards already running on it are cancelled and handed to another agent with their work kept (`Runner.evictPool`, the stall watchdog's hand-back without the wait), and one message says so. It stays out, even when it comes back, until a person presses **Put back in rotation** (`POST /api/pools/:id/restore`; `ih pool restore`, which the skill file lists among the decisions an agent may not take). A periodic check that merely fails does not eject; subscription pools keep the lockouts and the stall watchdog.

**Known gaps:**
- Operator REST routes (and so file reads and settings) are reachable without a token from other processes on the machine unless `IH_REQUIRE_TOKEN=1`.
- Shell checks are lexical (`$HOME/…`, scripts and variables are not seen). Real containment needs the Docker executor.
- Kimi and Codex edit inside their cwd without asking (leases don't stop them at edit time), which is why direct boards rely on the planner giving each card its own files. Codex's shell has no network (`needs_network` skips it).
- A turn that "succeeds" without doing the task is only caught by tests and Kev scoring. A planner that creates no cards ends in Review with nothing; it should be flagged.
- Routing knows quality and quota but **not speed**: the slowest agent can win a card on its prior (observed seconds per card per agent are not recorded).
- A command's output arrives only when it finishes (Kimi, Agy) or in part (Codex); a long build shows nothing until the end. The ACP terminal capability would fix it for Kimi (§5.1).
- Old failed-run outcomes recorded for an unreachable model before Phase 8 still count against it (there is no "ignore" pass over them).
- A second daemon instance still shares `.infinity-harness/opencode/opencode.json` and the API token file with the first (state, database and ports are separate); building a config without `.env` loaded drops the NIM and local providers from that file until the next real start.
- Reviewers' own outcomes aren't recorded. Kimi has no config isolation. Hardware (flashing a board) needs a human.
- Publisher id and license on the VS Code extension are placeholders; the GitHub workflow never ran.

## 9. Risks

| Risk | Mitigation |
|---|---|
| Vendor CLI updates break adapters (Kimi went 2.4 to 2.5 during Phase 7) | Adapter contract tests with a scripted fake agent; versions shown; live smoke after upgrades |
| Claude Pro quota too small even for orchestration | Reserve for the orchestrator; any pool can orchestrate |

| A plan that runs as a chain, or a board that runs one card at a time, makes parallel agents no faster than one | The planner is told the board's width and how to cut for it; the plan's waves are reported as it is built; direct boards run three workers by default |
| An outage looks like a bad model (a down endpoint scored 0 and kept getting cards) | Unreachable-provider failures are never blamed; the endpoint is checked and the pool taken out of rotation until a person restores it |

## 12. MCP hub and agent notes (Phase 9, built 2026-11-13)
IH hosts MCP servers once per machine and shares them through a hub (`/hub/<id>`, authenticated with the session token an agent already has; the server's own address and secrets never reach an agent). The library is per machine (Settings → MCP, `ih mcp`); each board has an **MCP** tab to switch servers on, save presets, and set which agents may use each one (`off | read | full`; read = tools the server marks `readOnlyHint`, overridable per tool). A server that drives one shared real thing (an open Roblox Studio place) serves changes one at a time. The planner is told what is on and who may use it; `create_subtask` takes `needs_mcp` (the router skips agents without access and the call is refused if nobody on the team may) and `prefers`. Agents carry up to six short **notes** (UI DEV, CODE REVIEW…): planners see them, Kev answers one yes/no question per note, and the router multiplies an agent's score by `1 + noteWeight × fit` (at most 2×, default weight 0.5), so notes nudge and never override a routing rule. Roblox Studio (`@chrrxs/robloxstudio-mcp` 3.4.3, run on Vinegar) ships in the library, with RbxSync's MCP server. **Add-ons** (`apps/daemon/src/addons.ts`, off by default, per board) bundle servers with a helper process in the board's folder: the Roblox add-on, for direct boards only, runs `rbxsync init` (only if `rbxsync.json` is missing; it never overwrites) and `rbxsync serve` with the board's folder as its working directory, and switches on both servers; one board holds the sync at a time (port 44755; `IH_RBXSYNC_PORT` moves it), a second board can take it over, and a port something else holds is reported rather than mistaken for it. **Token-burn controls (from the first real Roblox run):** per-server tool allowlists (`toolAllow`; Studio offers 27 of its 50 tools, RbxSync 2 of 48), add-on guides and `addon_status`, a health gate (`addonGate`) that holds cards while Studio's plugins are disconnected, a hub circuit breaker with a per-server `unavailableHint`, `ask_parent` (a stuck worker asks the agent that planned it), a person's stop that stays stopped (`Runner.cancel(…, {by, requeue:false})`; the daemon's own cancels still requeue), and `/api/boards/:id/efficiency` / `ih report` / the Metrics table. Add-ons are switched only with their own endpoints (`/api/boards/:id/addons/:addon/enable|disable`, `ih addon`), never through the settings patch. Plan, what was checked on real agents and what is not done (live Studio edit, other harnesses, grants storage, reviewers, VS Code and TUI views): [mcp-hub-plan.md](mcp-hub-plan.md) §0.
